## Multiple-choice explanations

**1. M02-Q01** — correct answer **D: Training data, label set, feature pipeline**

Training-time assets are those that determine what the model learns; the other lists are serving-time components that shape what happens to a request.

- **A** — An index is retrieved at request time and does not change the weights.
- **B** — These are serving controls and credentials, not things a model learns from.
- **C** — Prompts and tool schemas act at request time, after the model is fixed.

**2. M02-Q02** — correct answer **C: It can be made to reproduce or reveal properties of individual training rows.**

Capacity far exceeding data lets the model encode individual records, which is the mechanism behind membership inference and inversion; it is a privacy weakness created by fitting.

- **A** — Memorisation is precisely what makes individual rows recoverable.
- **B** — Zero training loss usually means a sharper, more fragile decision boundary.
- **D** — Extraction depends on query access, not on how well the model fits.

**3. M02-Q03** — correct answer **B: Grey-box**

Partial knowledge of the model, such as architecture without weights, is the standard definition of grey-box access; it is enough to train a substitute model.

- **A** — White-box means access to weights and gradients.
- **C** — Black-box means only input and output are visible.
- **D** — Architecture knowledge is real information, so 'no access' is wrong.

**4. M02-Q04** — correct answer **A: Returning a label instead of a probability vector**

Each probability is a supervised signal; a label is one bit. Coarser output lowers the information per query, which raises the budget an extraction attack needs.

- **B** — A model card informs defenders and attackers alike without removing signal.
- **C** — Reducing parameters changes the model, which was excluded, and may reduce utility.
- **D** — Logging is a detection control, not a reduction in the information returned.

**5. M02-Q05** — correct answer **D: The larger model memorises more, so privacy risk is higher.**

Capacity gives a model more room to encode individual records, and memorisation is the raw material of membership inference; equal accuracy does not imply equal leakage.

- **A** — Accuracy parity says nothing about leakage or robustness.
- **B** — Poisoning cost depends on data influence, not straightforwardly on size, and extraction depends on output granularity.
- **C** — Capacity does not confer immunity; if anything it enlarges the input region an attacker can exploit.

**6. M02-Q06** — correct answer **C: At annotation, when labels can be flipped deliberately**

Labels are an attack surface: a compromised annotator or feed can flip them, and a model will learn the flipped rule as faithfully as any other.

- **A** — Caching changes exposure over time, not what the model learned.
- **B** — Container building concerns artefact integrity, not label truth.
- **D** — Monitoring observes effects; it does not create label risk.

**7. M02-Q07** — correct answer **B: Substitute models trained on queries transfer attacks effectively.**

Transferability means an attacker can attack a model they trained themselves and reuse the inputs, so secrecy raises cost without removing the capability.

- **A** — Most commercial weights are not published; that is not the argument's weakness.
- **C** — Weights can be encrypted; the objection is about attack transfer, not storage.
- **D** — Secrecy blocks white-box gradients but not black-box or transfer attacks.

**8. M02-Q08** — correct answer **A: A stronger extraction and adversarial signal**

Full logits give an attacker far more information per query than a label, which lowers the cost of both extraction and gradient-free evasion.

- **B** — Storage cost is real but secondary to the information exposure.
- **C** — Latency is an operational concern, not the security consequence.
- **D** — Serving logits does not change the weights.

**9. M02-Q09** — correct answer **D: The information returned per query and the query budget**

Extraction is an information-acquisition problem: how much signal each response carries and how many responses the attacker can afford determine the fidelity of the copy.

- **A** — Depth changes the function, not the per-query information.
- **B** — Training-set size is invisible to a query-only attacker.
- **C** — Language and framework affect latency, not the attack's economics.

**10. M02-Q10** — correct answer **C: The model learns correlations that can re-identify a person without any name.**

A model encodes statistical relationships, and those relationships can single out a record even when every direct identifier was removed before training.

- **A** — Quasi-identifiers and model outputs routinely re-identify records after name removal.
- **B** — The problem is not specific to images; tabular and text data leak in the same way.
- **D** — Encryption protects data at rest, not what the trained model reveals.

## Written model answers

<div class="sas-answer" id="m02-s1-answer"><p class="sas-item__head"><strong>M02-S1</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Name the three stages of a training pipeline where an attacker with different access could insert influence, and one control for each.</p><p class="sas-answer__label">Model answer</p><p>Collection: verify source provenance and sign the dataset. Labelling: measure annotator agreement and adjudicate disagreements. Feature and training code: review changes, pin dependencies and hash the artefact. Each control targets a different access path, which is why one control cannot cover the pipeline.</p></div>

<div class="sas-answer" id="m02-s2-answer"><p class="sas-item__head"><strong>M02-S2</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Explain in two sentences why a high-capacity model trained on few records is a privacy problem even if it never outputs a training row verbatim.</p><p class="sas-answer__label">Model answer</p><p>Capacity lets the model fit idiosyncrasies of individual records, so its outputs are statistically different for records it saw than for records it did not. That difference is enough for a membership-inference attack, which needs a ranking signal rather than verbatim recall.</p></div>

<div class="sas-answer" id="m02-c1-answer"><p class="sas-item__head"><strong>M02-C1</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Explain the relationship between training-set size, model capacity and memorisation, and why that relationship is a security property rather than a modelling detail.</p><p class="sas-answer__label">Model answer</p><p>Memorisation grows when capacity is large relative to the number and diversity of examples, because the model can fit noise and individual records rather than only the shared structure. It is a security property because the fitted idiosyncrasies become observable through outputs: membership inference, attribute inference and inversion all exploit the gap between how a model behaves on seen and unseen records. The defender's levers are data volume and diversity, capacity limits, regularisation and output granularity, and each of them trades utility against leakage.</p></div>

<div class="sas-answer" id="m02-c2-answer"><p class="sas-item__head"><strong>M02-C2</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">A colleague says 'we do not need a threat model; our model is a standard architecture'. Explain what that argument misses.</p><p class="sas-answer__label">Model answer</p><p>Architecture determines which attacks are technically possible, not which are relevant. Relevance comes from the deployment: what data is used, who can query the model, what the outputs reveal, what actions the system can take, and what happens to a person when it is wrong. Two deployments of the same architecture can differ by orders of magnitude in risk because their trust boundaries and consequences differ. A threat model is the step that connects a generic capability to a specific harm.</p></div>

<div class="sas-answer" id="m02-sc1-answer"><p class="sas-item__head"><strong>M02-SC1</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A team trains a churn model on 900 customer records with a 12-layer network and serves full probabilities to a mobile app. Identify the three most important security weaknesses and the cheapest fix for each.</p><p class="sas-answer__label">Model answer</p><p>First, capacity against 900 records invites memorisation: reduce capacity or add regularisation, and measure leakage with a membership test. Second, full probabilities in a client app give an extraction and inference signal: return a coarse score band instead. Third, the app is an untrusted client that can query at volume: add per-account quotas and log query patterns. Each fix is cheap because it changes an interface or a training choice rather than the product.</p></div>

<div class="sas-answer" id="m02-sc2-answer"><p class="sas-item__head"><strong>M02-SC2</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A hospital wants to share a trained model with a research partner but not the training data. Describe what the partner could still learn about patients, and one control that limits it.</p><p class="sas-answer__label">Model answer</p><p>The partner receives a function fitted to patient records: with query access they can run membership inference to test whether a specific patient was in the training set, attribute inference to estimate sensitive properties, and inversion to reconstruct a representative record. Controls include returning coarse outputs, limiting queries per researcher, applying differential privacy during training, and releasing the model under a data-use agreement with an audited query log. No single control removes the leak, so the assessment should quantify residual risk.</p></div>

<div class="sas-answer" id="m02-p1-answer"><p class="sas-item__head"><strong>M02-P1</strong> <span class="sas-meta">Practical programming · 8 marks</span></p><p class="sas-answer__q">Write a function `capacity_report(n_rows: int, n_params: int, train_acc: float, test_acc: float) -&gt; dict` that returns a parameter-to-row ratio, a memorisation gap and a risk band with a stated rule. Include a short test showing a 50,000-parameter model on 400 rows is flagged.</p><p class="sas-answer__label">Model answer</p><p>A complete answer computes `ratio = n_params / n_rows`, `gap = train_acc - test_acc`, and assigns a band from explicit thresholds, for example high when ratio &gt; 20 or gap &gt; 0.15, medium when ratio &gt; 5 or gap &gt; 0.05, else low. The report should include the thresholds in the returned dict so the decision is auditable rather than implied. The test builds the 50,000/400 case, asserts the band is 'high', and asserts the ratio is returned, which also documents that the ratio alone drives the band in that example.</p></div>

<div class="sas-answer" id="m02-ct1-answer"><p class="sas-item__head"><strong>M02-CT1</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">A vendor offers 'privacy-preserving inference' that adds noise to outputs. What questions decide whether that claim means anything?</p><p class="sas-answer__label">Model answer</p><p>Ask what the noise is calibrated to: a formal guarantee such as epsilon-differential privacy with a stated epsilon and mechanism, or an unspecified perturbation. Ask what is protected against: membership, attribute inference, reconstruction or only casual inspection. Ask whether the noise is applied before or after aggregation across queries, since repeated noisy answers average out. Ask what utility cost was measured. Without an epsilon, a threat model and a composition argument, 'privacy-preserving' is a description of an implementation detail rather than a property.</p></div>

<div class="sas-answer" id="m02-ct2-answer"><p class="sas-item__head"><strong>M02-CT2</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">You must choose between publishing a model's weights and serving it behind an API. Argue the security trade-off rather than picking a side.</p><p class="sas-answer__label">Model answer</p><p>Publishing weights gives away the capability permanently and enables white-box attacks, extraction-free copying and offline privacy attacks, but it also enables external scrutiny and reproducibility. Serving behind an API preserves control: you can rate limit, coarsen outputs, monitor and revoke, at the cost of a query surface and an operational burden. The decision hinges on whether the model's value is the weights or the service, and on whether regulators or partners require inspection. A defensible answer names the assumption that would flip the recommendation.</p></div>
