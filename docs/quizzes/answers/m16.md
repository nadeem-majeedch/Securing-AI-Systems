## Multiple-choice explanations

**1. M16-Q01** — correct answer **A: 422 Unprocessable Entity**

A validation failure is a client error with a clear classification; 422 keeps monitoring honest because real server faults stay distinguishable.

- **B** — A 200 hides failures from monitoring and from clients.
- **C** — A 500 reports a server fault where the client sent bad data.
- **D** — A redirect does not describe validation.

**2. M16-Q02** — correct answer **D: Compute and memory per request become bounded, so one client cannot consume the pool**

Cost per request scales with input size, so an unbounded length lets a single caller exhaust capacity; a cap converts an unbounded cost into a fixed one.

- **A** — Length is not a reliable indicator of intent.
- **B** — Authentication is a separate control.
- **C** — Injection can occur in short inputs.

**3. M16-Q03** — correct answer **C: It discloses file paths, library versions and internal structure that aid an attacker**

Error detail is reconnaissance: paths, versions and internal names help an attacker choose an exploit, and a correlation ID gives the same debugging value without disclosure.

- **A** — Latency is minor and not the risk.
- **B** — Clients can retry regardless.
- **D** — Storage cost is trivial.

**4. M16-Q04** — correct answer **B: It stops one tenant from consuming capacity that others need**

A global limit protects the service from total overload but lets a single tenant dominate it; per-tenant quotas protect fairness as well as availability.

- **A** — Quotas do not increase throughput.
- **C** — Authentication remains necessary.
- **D** — Accuracy is a model property.

**5. M16-Q05** — correct answer **A: Redacting secrets and personal data, and restricting access with a retention period**

Prompt logs are a secondary copy of sensitive text, so minimisation, access control and retention determine the breach impact.

- **B** — Compression reduces size, not exposure.
- **C** — A higher log level increases exposure.
- **D** — Sampling reduces volume but not the sensitivity of what is kept.

**6. M16-Q06** — correct answer **D: The caller can name any tenant, so authorisation depends on an untrusted value**

The tenant must be derived from the authenticated principal, not supplied by the caller, otherwise changing one field crosses a boundary.

- **A** — Transport encryption covers the body.
- **B** — Caching is unrelated to authorisation.
- **C** — Length is not the issue.

**7. M16-Q07** — correct answer **C: Rejecting unexpected fields and wrong types**

Type and shape checks belong at the edge so malformed requests never reach the model, and so every client gets the same contract.

- **A** — Temperature is a service-level choice, not input validation.
- **B** — Checkpoints are deployment configuration.
- **D** — Thresholds are policy decisions made deeper in the service.

**8. M16-Q08** — correct answer **B: A request timeout, bounded retries with jitter and a queue for overload**

Timeouts bound resource holding, bounded retries prevent amplification and a queue converts overload into latency rather than failure.

- **A** — This is the configuration that turns a slow dependency into an outage.
- **C** — Longer timeouts increase resource holding.
- **D** — Caching is useful but does not address overload.

**9. M16-Q09** — correct answer **A: It links the user's report to internal logs without disclosing internals**

The ID is a pointer into logs only the operator can read, which preserves debuggability and keeps the response free of internal detail.

- **B** — It grants no authority.
- **C** — It complements logging rather than replacing it.
- **D** — Forgery of an ID is harmless because it grants nothing.

**10. M16-Q10** — correct answer **D: Authorisation denials with principal, action and reason**

Denials record attempts that were refused, which is where probing and privilege escalation appear first.

- **A** — Full payloads create exposure and are rarely needed for detection.
- **B** — Image size is inventory metadata.
- **C** — Startup accuracy is not an event stream.

## Written model answers

<div class="sas-answer" id="m16-s1-answer"><p class="sas-item__head"><strong>M16-S1</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Explain in two sentences why authentication alone does not secure a prediction API.</p><p class="sas-answer__label">Model answer</p><p>Authentication establishes who is calling, not what they may do or how much they may consume. Authorisation, input validation, quotas and output constraints are separate controls, and an authenticated attacker with unlimited queries is the normal case for extraction and privacy attacks.</p></div>

<div class="sas-answer" id="m16-s2-answer"><p class="sas-item__head"><strong>M16-S2</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">State the security argument for returning a coarse label instead of a probability vector.</p><p class="sas-answer__label">Model answer</p><p>A probability vector reveals confidence across classes, which is the signal used for extraction and for membership inference. A coarse label returns one bit, so the same attack needs far more queries to learn as much.</p></div>

<div class="sas-answer" id="m16-c1-answer"><p class="sas-item__head"><strong>M16-C1</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Explain how an API can be secure against malformed input and still be vulnerable to extraction, using the distinction between validation and authorisation of use.</p><p class="sas-answer__label">Model answer</p><p>Validation ensures each request is well formed, within size limits and of the expected type; it says nothing about how many requests a principal may make or what pattern they form. Extraction uses perfectly valid requests in volume, so the control that matters is authorisation of use: quotas, per-principal accounting, coarser output and monitoring of query similarity. A service can pass every schema test and still hand over its decision function, which is why boundary validation and usage policy are separate layers.</p></div>

<div class="sas-answer" id="m16-c2-answer"><p class="sas-item__head"><strong>M16-C2</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">A team proposes logging every request body to 'improve the model later'. Give the security assessment and a design that keeps most of the value.</p><p class="sas-answer__label">Model answer</p><p>Full body logging creates a secondary store of personal data, secrets and injected content, usually with weaker access control and longer retention than the primary system, and it widens the impact of any log compromise. A better design logs metadata needed for operations, such as principal, endpoint, latency, status and a content hash, plus sampled and redacted payloads under a short retention with restricted access and a documented purpose. If data is genuinely needed for training, it should flow through a governed dataset pipeline with consent and provenance, not through log scraping.</p></div>

<div class="sas-answer" id="m16-sc1-answer"><p class="sas-item__head"><strong>M16-SC1</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">You inherit a prediction API with no owner, no schema, no quotas and verbose errors. Produce the first-day remediation list in priority order.</p><p class="sas-answer__label">Model answer</p><p>First, stop the leak: replace verbose errors with a generic message plus a correlation ID. Second, close the boundary: require authentication and derive the tenant from the credential. Third, add schema validation and a maximum input length so malformed and oversized requests are rejected before the model. Fourth, add per-principal quotas and a timeout. Fifth, begin logging denials and query patterns. The order is chosen by exposure per hour of work, and each step is reversible, which matters when the service has no owner to approve risk.</p></div>

<div class="sas-answer" id="m16-sc2-answer"><p class="sas-item__head"><strong>M16-SC2</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A mobile app calls the model API directly with an embedded key. Explain the exposure and the redesign.</p><p class="sas-answer__label">Model answer</p><p>An embedded key is extractable from the app binary, so the app's quota and identity become the attacker's, and there is no per-user attribution. The redesign puts a backend-for-frontend between app and model: the app authenticates a user, the backend holds the model credential, derives entitlements, applies per-user quotas and returns coarse results. The key rotation problem also disappears, because only the backend holds a secret that can be rotated without shipping a new app.</p></div>

<div class="sas-answer" id="m16-p1-answer"><p class="sas-item__head"><strong>M16-P1</strong> <span class="sas-meta">Practical programming · 8 marks</span></p><p class="sas-answer__q">Write two FastAPI endpoints, one insecure and one hardened (schema, length limit, API key), send eight probes to both with TestClient, and assert 401/422 instead of 500.</p><p class="sas-answer__label">Model answer</p><p>A complete implementation defines a Pydantic model with a maximum length, reads the key from a header and returns 401 when it is absent or wrong; FastAPI then returns 422 for schema violations automatically. The probes cover valid input, missing auth, missing field, wrong type, empty text, oversized text, an extra field and a nested object. Assertions check that the hardened endpoint returns 401 or 422 for every invalid case and 200 for the valid one, and the comparison table shows the insecure app returning 200 with an error body, which is why monitoring misses the failures.</p></div>

<div class="sas-answer" id="m16-ct1-answer"><p class="sas-item__head"><strong>M16-CT1</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">A product team wants to remove rate limits to improve the customer experience. Argue the security consequence and offer a compromise.</p><p class="sas-answer__label">Model answer</p><p>Removing limits makes extraction, credential stuffing and cost exhaustion cheap, and it converts any client bug into a service-wide incident; the experience improves for legitimate users and for attackers equally. The compromise is tiered limits with burst allowances: a token bucket sized to observed legitimate peaks, higher ceilings for contracted clients with audit, and an export quota independent of request rate. That preserves responsiveness for normal use while keeping the cost of systematic probing above what an attacker will pay.</p></div>

<div class="sas-answer" id="m16-ct2-answer"><p class="sas-item__head"><strong>M16-CT2</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">You must choose between a web application firewall and per-principal quotas for an AI API. Argue the choice and state the assumption.</p><p class="sas-answer__label">Model answer</p><p>Quotas act on the resource attacks actually consume, which is queries and information, and they apply to authenticated principals, so they change the economics of extraction and abuse. A WAF acts on request shape and known signatures, which is useful against generic injection and scanning but blind to a well-formed, high-volume campaign from a valid account. Prefer quotas unless the API is already well instrumented and the dominant threat is generic web exploitation; that is the assumption that would reverse the choice.</p></div>
