## Multiple-choice explanations

**1. M14-Q01** — correct answer **C: In the tool execution layer, before the action runs**

The model proposes actions; the execution layer disposes. Only code outside the model can refuse a call regardless of how persuasive the conversation was.

- **A** — A prompt rule competes with injected text and cannot refuse anything.
- **B** — Fine-tuning shapes behaviour but provides no guarantee per call.
- **D** — A warning does not stop the call.

**2. M14-Q02** — correct answer **B: A confused deputy: the agent's authority is used for a request the customer may not be entitled to**

The agent lends its own privileges to whoever supplies the text, so the customer's entitlement must be checked against the authenticated principal before execution.

- **A** — Latency is not the security failure.
- **C** — Identifier validation is separate from the authority problem.
- **D** — Hallucination is a quality risk, not this failure.

**3. M14-Q03** — correct answer **A: A delegated token scoped to the user, the domain and a daily send limit**

Delegation keeps the user in the authorisation chain and scoping bounds volume and recipients, so a successful injection inherits almost nothing.

- **B** — Organisation-wide send converts any injection into mass mailing.
- **C** — A stored shared password has no per-user attribution and cannot be scoped.
- **D** — An administrator key is the largest possible blast radius.

**4. M14-Q04** — correct answer **D: Deleting a record or sending an external payment**

Irreversible actions with external consequence are the confirmation boundary; reversible reads can be automated without shifting risk to the user.

- **A** — Reads are reversible and already permitted to the user.
- **B** — Search is a read operation.
- **C** — Summarisation has no external effect.

**5. M14-Q05** — correct answer **C: Principal, tenant, tool, arguments, decision, rule and reason**

The decision is a function of those fields, so recording them makes the outcome explainable and reproducible.

- **A** — The answer hides which call was attempted.
- **B** — Model and time identify the request but not the policy evaluation.
- **D** — Token counts are cost, not authorisation evidence.

**6. M14-Q06** — correct answer **B: The worker must not treat the planner's text as authority for actions the user did not grant**

Delegation between agents repeats the confused-deputy problem internally, so the worker's authorisation must be evaluated against the original principal, not the planner.

- **A** — Message exchange is a solved engineering problem.
- **C** — Latency is not the security issue.
- **D** — Logging is straightforward and necessary.

**7. M14-Q07** — correct answer **A: It can reach only the sites, methods and actions the task requires**

Least agency applies least privilege to actions: an allowlist of destinations and methods limits what a compromised plan can do.

- **B** — Unrestricted browsing is the exposure being limited.
- **C** — Asking the model is not a control.
- **D** — A full profile carries cookies and credentials into the agent's reach.

**8. M14-Q08** — correct answer **D: Validating the amount against the order record and a policy cap before execution**

The argument must be checked against authoritative data, not against the model's statement, because the model can be persuaded to supply any number.

- **A** — Rounding changes presentation, not authorisation.
- **B** — Logging records the loss rather than preventing it.
- **C** — A prompt rule is advisory.

**9. M14-Q09** — correct answer **C: The sandbox bounds what the code can reach when it runs, which is the actual exposure**

The harm comes from execution, so limiting filesystem, network and credentials bounds the consequence; filtering output is a weaker, post-hoc control.

- **A** — Sandboxing is unrelated to code quality.
- **B** — Output restrictions act after execution has happened.
- **D** — Authentication is still required for the tool itself.

**10. M14-Q10** — correct answer **B: It is append-only and records the effective principal per action**

An attacker who can edit the log removes the evidence, and a record without the effective principal cannot attribute the action.

- **A** — Co-location lets a compromised host rewrite history.
- **C** — Denied attempts are often the most informative entries.
- **D** — Sampling can drop the exact sequence under investigation.

## Written model answers

<div class="sas-answer" id="m14-s1-answer"><p class="sas-item__head"><strong>M14-S1</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Explain the confused-deputy problem for an agent in two sentences.</p><p class="sas-answer__label">Model answer</p><p>The agent holds authority the requester may not have, and it acts on text the requester controls, so it can be made to exercise that authority on their behalf. The fix is to authorise each action against the authenticated user's entitlements rather than against the agent's own credential.</p></div>

<div class="sas-answer" id="m14-s2-answer"><p class="sas-item__head"><strong>M14-S2</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Name three fields an agent audit record needs and say what each makes possible.</p><p class="sas-answer__label">Model answer</p><p>The effective principal allows attribution to a person or service. The tool and its arguments allow reconstruction of what was attempted. The decision, rule and reason allow review of why it was allowed or denied without replaying the agent.</p></div>

<div class="sas-answer" id="m14-c1-answer"><p class="sas-item__head"><strong>M14-C1</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Explain why 'the agent is instructed to stay within the tenant' is not an authorisation control, using the notion of a trust boundary.</p><p class="sas-answer__label">Model answer</p><p>A trust boundary is where authority changes, and text inside the model does not change authority: the tenant check has to be evaluated by the service against the authenticated principal. An instruction is one token sequence among many and can be contradicted by injected content or simply ignored under pressure from a plausible request. The control that works is a policy engine that derives the tenant from the credential, refuses cross-tenant resources and records the decision, so the boundary exists in code rather than in the prompt.</p></div>

<div class="sas-answer" id="m14-c2-answer"><p class="sas-item__head"><strong>M14-C2</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Design the confirmation policy for an agent with read, write and payment tools, and justify where you place the line.</p><p class="sas-answer__label">Model answer</p><p>Reads of resources the user can already access run without confirmation, because the action is reversible and already within their authority. Writes that are reversible, such as drafting a document, can run with an undo path and a visible diff. Irreversible or externally visible actions, such as sending an email to an external address, deleting records or moving money, require explicit confirmation showing the arguments, with a cap above which a second approver is needed. The line sits at irreversibility and external effect, because those are the properties that make an error unrecoverable.</p></div>

<div class="sas-answer" id="m14-sc1-answer"><p class="sas-item__head"><strong>M14-SC1</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A support agent has file, email and refund tools. Compute its effective permissions and reduce them, stating what each reduction costs.</p><p class="sas-answer__label">Model answer</p><p>Effective permissions today are the union of everything the service account can do, applied to any customer the conversation mentions. Reduce to: files scoped to the requesting customer's attachments, email limited to internal domains with a daily cap, refunds capped at a low amount with validation against the order record, and no other tools. Costs are fewer self-service cases and some manual handling above the cap, which is the price of bounding an injection's consequence. The analysis should show the before and after permission sets explicitly, because a verbal description hides the union.</p></div>

<div class="sas-answer" id="m14-sc2-answer"><p class="sas-item__head"><strong>M14-SC2</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">An agent can install Python packages to answer data questions. Describe the exposure and the containment you would require.</p><p class="sas-answer__label">Model answer</p><p>Package installation is code execution with the agent's network and filesystem access, so a malicious or typosquatted package can exfiltrate data or persist. Containment: run in an ephemeral sandbox with no credentials, an allowlisted package index, egress disabled except to the index, CPU and time limits, and no access to production data beyond a read-only sample. Any output that leaves the sandbox is data, not authority, and the package list should be recorded per run so an incident can be reconstructed.</p></div>

<div class="sas-answer" id="m14-p1-answer"><p class="sas-item__head"><strong>M14-P1</strong> <span class="sas-meta">Practical programming · 8 marks</span></p><p class="sas-answer__q">Implement `authorise(request, principals, policy)` with deny-by-default, checks for principal, action, role, resource tenant, amount and recipient, and an audit row per decision. Assert at least five denials on a ten-request set.</p><p class="sas-answer__label">Model answer</p><p>A complete implementation orders the checks so the cheapest decisive rule runs first and every branch returns a rule name. It derives the tenant from the principal, never from the request, and validates amounts against a policy cap. The audit row records request id, principal, tool, arguments, decision, rule and reason. Tests assert specific denial reasons for cross-tenant resources, over-limit amounts, unknown actions and unknown principals, and assert that legitimate requests still pass, because a policy that denies everything is not a control.</p></div>

<div class="sas-answer" id="m14-ct1-answer"><p class="sas-item__head"><strong>M14-CT1</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">A team wants to give an agent full API access 'so it can recover from unexpected situations'. Argue against it and offer the alternative.</p><p class="sas-answer__label">Model answer</p><p>Broad access converts every prompt-level failure into an unbounded action, and 'recover from unexpected situations' is precisely the condition an attacker creates: the agent is most likely to improvise when the conversation is adversarial. The alternative is a small allowlist plus an escalation path, where the agent can request a human-approved action or a temporary, scoped credential for a named task. That keeps the recovery capability while making the grant explicit, time-bounded and auditable.</p></div>

<div class="sas-answer" id="m14-ct2-answer"><p class="sas-item__head"><strong>M14-CT2</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">You must decide whether an agent's actions should be attributed to the user or to the service. Argue both and recommend one for a payments agent.</p><p class="sas-answer__label">Model answer</p><p>Attributing to the service simplifies implementation and centralises control but erases the person behind the action, which breaks least privilege and makes abuse hard to detect. Attributing to the user preserves entitlement checks and attribution but requires delegation tokens, per-user quotas and a way to handle users who cannot consent in the moment. For a payments agent, attribute to the user with a service-held constraint on amount and frequency, because the consequences are financial and reversible only by a human; the service should hold the ceiling, not the permission.</p></div>
