## Multiple-choice explanations

**1. M03-Q01** — correct answer **A: Authentication proves identity; authorisation decides permitted actions.**

Authentication answers who is calling; authorisation answers what that caller may do. Confusing them produces services that verify a token and then allow any action.

- **B** — This reverses the definitions.
- **C** — They are distinct decisions made at different points in a request.
- **D** — Both apply to humans and services; the split is identity versus permission.

**2. M03-Q02** — correct answer **D: A dedicated service identity scoped to those two paths**

A scoped service identity limits what a compromised job can reach; shared and personal credentials turn one compromised workload into an account-wide incident.

- **A** — Shared accounts remove attribution and grant far more than the job needs.
- **B** — Personal tokens cannot be rotated without breaking the person and leak on departure.
- **C** — Administrator rights convert any code execution in training into cluster compromise.

**3. M03-Q03** — correct answer **C: A cryptographic hash recorded in a trusted manifest**

Integrity needs a digest compared against a value stored where the attacker cannot also change it; encryption hides content and encoding hides nothing.

- **A** — Encryption protects confidentiality, and modified ciphertext may still decrypt to something.
- **B** — A password hash is for verifying a secret the verifier does not store, not a file's identity.
- **D** — Encoding is reversible formatting, not a security control.

**4. M03-Q04** — correct answer **B: Assurance that the message came from someone holding the key**

A hash binds content to a value; a MAC binds content to a key holder, which is what stops an attacker from recomputing the digest after modifying the data.

- **A** — Performance is not the distinction, and MACs are typically slower.
- **C** — MACs do not compress; they authenticate.
- **D** — Neither primitive is reversible, by design.

**5. M03-Q05** — correct answer **A: Rotate the key, then purge it from history**

Once a key has been exposed, assume it is compromised; rotation limits the damage, and history rewriting removes the copy that clones and caches still hold.

- **B** — Deleting the cell leaves the value in version history and caches.
- **C** — A comment is still plaintext in the same repository.
- **D** — Renaming changes path, not exposure.

**6. M03-Q06** — correct answer **D: It limits what a compromised job can reach, including data stores and metadata services.**

Training code often runs as high-privilege batch work with access to large data stores; segmentation means an exploit in that code cannot reach unrelated systems.

- **A** — Segmentation is a control on reachability, not on compute performance.
- **B** — Overfitting is a modelling property unrelated to network topology.
- **C** — It complements authentication rather than replacing it.

**7. M03-Q07** — correct answer **C: Per-principal request volume, output size and query similarity**

Extraction appears as many similar queries from one principal with consistent output sizes; per-principal detail is what makes the pattern visible and attributable.

- **A** — Daily aggregates hide the burst and the principal.
- **B** — Training accuracy says nothing about query behaviour.
- **D** — Base-image choice is an inventory fact, not evidence of an attack.

**8. M03-Q08** — correct answer **B: The model service cannot audit the original user**

Forwarding with a shared credential erases the end user from the authorisation and audit trail, so every request looks like the tool and per-user policy cannot be enforced.

- **A** — Latency is unrelated to the credential design.
- **C** — Accuracy does not depend on which principal made the call.
- **D** — Rotation is a management detail, not the security flaw.

**9. M03-Q09** — correct answer **A: Read-only filesystem and a scoped token for one data source**

Blast radius is set by what the compromised process can touch: an immutable filesystem and a narrow token mean the attacker inherits almost nothing.

- **B** — Key length does not limit what the process can reach once compromised.
- **C** — More memory improves throughput, not containment.
- **D** — Verbose errors typically help the attacker.

**10. M03-Q10** — correct answer **D: They can be read by any process in the container and captured in crash dumps.**

Environment variables are plaintext in the process environment, so code execution or a diagnostic dump exposes them; a secret manager with short-lived credentials reduces that exposure.

- **A** — Runtimes do not encrypt the process environment.
- **B** — Length limits are irrelevant to the exposure.
- **C** — Rotation is possible; the flaw is readability.

<div class="sas-answer" id="m03-s1-answer"><p class="sas-item__head"><strong>M03-S1</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Explain in two sentences why a shared service account for all model training jobs is a security problem even when every engineer is trusted.</p><p class="sas-answer__label">Model answer</p><p>A shared account removes attribution, so no log can show which job or person performed an action. It also means one compromised or buggy job inherits every permission any other job needs, which turns a single exploit into account-wide access.</p></div>

<div class="sas-answer" id="m03-s2-answer"><p class="sas-item__head"><strong>M03-S2</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">State when to use a hash, when to use a MAC and when to use encryption, in one line each.</p><p class="sas-answer__label">Model answer</p><p>Use a hash to compare content against a trusted value, such as a file digest in a manifest. Use a MAC when the verifier shares a key and must detect forged modifications. Use encryption when the content itself must remain confidential, not merely unmodified.</p></div>

<div class="sas-answer" id="m03-c1-answer"><p class="sas-item__head"><strong>M03-C1</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Explain least privilege for an ML platform using the three identities that usually exist: the data engineer, the training job and the serving container.</p><p class="sas-answer__label">Model answer</p><p>Each identity should hold only the permissions its function requires. The data engineer needs write access to the curated store and read access to raw, with change review. The training job needs read on one dataset path, write to one experiment registry and no access to production secrets. The serving container needs read on one model artefact and the ability to write predictions to one sink, with no route to training data. The value comes from separation: a compromise of any one identity cannot reach the others' assets, and an audit can attribute each action.</p></div>

<div class="sas-answer" id="m03-c2-answer"><p class="sas-item__head"><strong>M03-C2</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Why is 'we are behind the VPN' an incomplete answer to an authorisation question? Explain with a concrete AI example.</p><p class="sas-answer__label">Model answer</p><p>A VPN answers whether a network path exists, not what the caller may do once connected. An internal analytics tool that forwards user prompts to a model with its own broad credential gives every internal user the tool's authority, so a support agent can trigger actions reserved for administrators. The example shows that authorisation must be evaluated per request against the actual principal, independent of network location, because the perimeter cannot distinguish one internal caller from another.</p></div>

<div class="sas-answer" id="m03-sc1-answer"><p class="sas-item__head"><strong>M03-SC1</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A model API is reachable from the internet and from an internal agent. Design the authentication and authorisation split, naming the token type and the check at each hop.</p><p class="sas-answer__label">Model answer</p><p>External clients authenticate with short-lived OAuth tokens scoped to a tenant, and the gateway checks signature, expiry, audience and scope before routing. The internal agent authenticates as a workload identity and, on behalf of a user, carries a delegation token that names that user so the service can enforce per-user policy and attribute the request. The model service authorises the requested action, not just the caller, and never accepts a tenant identifier supplied in the body. Both hops log the effective principal.</p></div>

<div class="sas-answer" id="m03-sc2-answer"><p class="sas-item__head"><strong>M03-SC2</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A dataset shared with a partner is stored in a bucket with a public-read bucket policy. Outline the response in order, and say what you would preserve.</p><p class="sas-answer__label">Model answer</p><p>First remove public access and confirm the policy change has propagated, then rotate any credentials that were in the bucket. Next determine exposure: enable access logs if they exist, and reconstruct which objects were fetched and by whom. Preserve logs and object versions before cleanup, because they are the only evidence of scope. Then assess notification obligations, and only afterwards redesign access using signed URLs with short expiry and per-partner prefixes. Preserving evidence before deletion is the step teams most often skip.</p></div>

<div class="sas-answer" id="m03-p1-answer"><p class="sas-item__head"><strong>M03-P1</strong> <span class="sas-meta">Practical programming · 8 marks</span></p><p class="sas-answer__q">Write `check_request(token_claims: dict, request: dict, policy: dict) -&gt; tuple[str, str]` that returns a decision and a rule name, enforcing audience, scope, tenant match and action allowlist. Include tests for a valid request, a wrong tenant and an unlisted action.</p><p class="sas-answer__label">Model answer</p><p>A complete implementation checks, in a fixed order, that the token is unexpired, that `aud` equals the service identifier, that the required scope is present, that the tenant in the request equals the tenant in the token and that the action appears in the policy's allowlist for that role. Each failure returns a distinct rule name so the decision is auditable, and default is deny. Tests assert an allowed request returns ('allow', 'all_checks_passed'), a mismatched tenant returns ('deny', 'tenant_match'), and an action absent from the allowlist returns ('deny', 'action_allowlisted').</p></div>

<div class="sas-answer" id="m03-ct1-answer"><p class="sas-item__head"><strong>M03-CT1</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">A team proposes storing model artefacts in a bucket protected by 'security through obscurity': a long random prefix and no listing. Argue why this is not an access control, and what replaces it.</p><p class="sas-answer__label">Model answer</p><p>An unguessable path is a secret shared with every client that needs it, and secrets leak through logs, browser history, referrers and support tickets; once leaked, the prefix is a valid capability with no revocation. Obscurity also provides no attribution, so an exposure cannot be scoped. Replace it with authenticated access, per-principal authorisation, short-lived signed URLs, access logging and object-level encryption, so that possession of a URL is not sufficient and every fetch has an identity behind it.</p></div>

<div class="sas-answer" id="m03-ct2-answer"><p class="sas-item__head"><strong>M03-CT2</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">Your organisation wants one 'AI platform' credential shared by data science, training and serving to simplify operations. Make the strongest case against it, then say what you would concede.</p><p class="sas-answer__label">Model answer</p><p>The case against is that a single credential collapses three trust boundaries: a notebook mistake can reach production data, a compromised training job can alter served models, and no log can attribute an action to a team. Blast radius, attribution and least privilege all degrade at once, and rotation becomes a coordinated outage risk. What you can concede is operational convenience: a platform team can issue short-lived credentials automatically per workload, which preserves the single workflow while keeping identities separate. The concession is about tooling, not about merging identities.</p></div>
