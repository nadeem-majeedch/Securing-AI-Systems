## Multiple-choice explanations

**1. M15-Q01** — correct answer **D: Third-party instruction data accepted without provenance checks**

Instruction data is text an attacker can author, and a small poisoned subset can install a trigger while leaving benchmark scores intact.

- **A** — Review is the control that makes a dataset safer, not the risk.
- **B** — Schedules affect training dynamics, not data integrity.
- **C** — Hyperparameters do not carry attacker-controlled content.

**2. M15-Q02** — correct answer **C: The pickle format can encode arbitrary object construction, which executes on load**

Deserialisation reconstructs objects by calling constructors and reducers, so a crafted payload runs code before any model is evaluated.

- **A** — Pickle is a serialisation format, not compiled bytecode.
- **B** — There is no shell header; the risk is in the opcodes.
- **D** — The risk exists even when no main block is present.

**3. M15-Q03** — correct answer **B: That the manifest itself came from the expected publisher**

Hashes compare content with a list; if the list travelled with the tampered bundle, everything matches, which is why the manifest needs a signature or an independent channel.

- **A** — That is exactly what hashing establishes.
- **C** — Completeness is checkable against the listed files.
- **D** — A modified file changes its digest and is detected.

**4. M15-Q04** — correct answer **A: A lockfile with pinned versions and hashes**

Pinning with hashes makes the resolved artefact verifiable and prevents silent substitution between builds.

- **B** — Latest-at-runtime makes builds non-reproducible and unpredictable.
- **C** — Git branches move and cannot be verified by hash.
- **D** — Sharing an environment spreads risk rather than controlling it.

**5. M15-Q05** — correct answer **D: The base model's safety training was overridden by the new data distribution**

Fine-tuning shifts behaviour toward the training distribution, and a corpus that contains compliant answers teaches compliance, which is why safety evaluation must be repeated after every fine-tune.

- **A** — A low learning rate would produce little change, not this change.
- **B** — Parameter count does not change in a standard fine-tune.
- **C** — Tokeniser changes are unrelated to refusal behaviour here.

**6. M15-Q06** — correct answer **C: The artefact can change under the same name, so the review you performed may not describe what runs**

Names are mutable references; without a digest you cannot tell whether the artefact you audited is the artefact you deployed.

- **A** — Performance is not the risk.
- **B** — Hub policy varies and does not protect you from substitution.
- **D** — Loading succeeds, which is the problem.

**7. M15-Q07** — correct answer **B: Licence, provenance, reviewer, transformation history and a content hash**

Those fields make the source auditable and the artefact reproducible, which is what an incident review needs.

- **A** — Size and date do not establish origin or permission.
- **C** — The model is a consumer of the data.
- **D** — Compute cost is unrelated to provenance.

**8. M15-Q08** — correct answer **A: Safetensors with a verified manifest**

Safetensors stores tensors in a data-only format, so loading cannot execute a payload; the manifest addresses integrity separately.

- **B** — A checksum in the name is not verified and pickle still executes.
- **C** — A Python module executes by import.
- **D** — Disabling `weights_only` enables the deserialisation path.

**9. M15-Q09** — correct answer **D: A held-out set of policy-violating requests with expected refusals**

Refusal behaviour needs its own test set, because general benchmarks do not measure whether the model declines what it should.

- **A** — General accuracy can rise while refusals disappear.
- **B** — Latency is unrelated.
- **C** — Loss describes fit, not policy behaviour.

**10. M15-Q10** — correct answer **C: A plausible misspelling resolves to an attacker-published package that installs instead**

The dependency resolver installs whatever name matches, so a near-miss name gives the attacker code execution in your build.

- **A** — Registries check that a name exists, not that it is the one you meant.
- **B** — Hashing is orthogonal to naming.
- **D** — Lockfiles record whatever was resolved, including a hostile package.

## Written model answers

<div class="sas-answer" id="m15-s1-answer"><p class="sas-item__head"><strong>M15-S1</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Explain in two sentences why a hash manifest inside the bundle is weaker evidence than a signed manifest kept separately.</p><p class="sas-answer__label">Model answer</p><p>A hash compares content with a list, so an attacker who modifies a file and updates the list inside the same bundle produces a matching pair. A signer's key, or a copy of the digest held in a separate channel, is what links the content to a publisher you chose to trust.</p></div>

<div class="sas-answer" id="m15-s2-answer"><p class="sas-item__head"><strong>M15-S2</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Name two things a fine-tuning risk assessment must check about the base model, not the data.</p><p class="sas-answer__label">Model answer</p><p>The base model's provenance and licence, including whether its weights may be used commercially and whether it has known backdoors or unsafe behaviour. Its artefact integrity, meaning the exact digest and format, because a substituted checkpoint changes everything downstream regardless of how clean your data is.</p></div>

<div class="sas-answer" id="m15-c1-answer"><p class="sas-item__head"><strong>M15-C1</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Explain why fine-tuning is a supply-chain step even when all the data is internal.</p><p class="sas-answer__label">Model answer</p><p>Fine-tuning combines four inherited artefacts: base weights, tokeniser and configuration, training code with its dependencies, and the data. Each is a trust decision, and only the last is internal. The base weights may carry a trigger, the tokeniser may differ from the one the safety evaluation assumed, and a dependency may execute at import. Treating the pipeline as a supply chain means recording digests for every input and re-running safety and behaviour evaluations on the output, because the output is a new artefact with a new risk profile.</p></div>

<div class="sas-answer" id="m15-c2-answer"><p class="sas-item__head"><strong>M15-C2</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">A team's model card claims fine-tuning 'preserved all safety properties'. What evidence would make that claim credible?</p><p class="sas-answer__label">Model answer</p><p>A pre-registered evaluation run on both base and tuned models with the same prompts, sampling parameters and scoring: refusal rates on a policy-violating set, over-refusal on benign prompts, and task accuracy. The claim needs the numbers and their confidence intervals, not the adjective, plus a statement of what was not tested such as multi-turn or adversarial phrasing. It also needs the exact digests of both models, because a claim about a name is a claim about nothing.</p></div>

<div class="sas-answer" id="m15-sc1-answer"><p class="sas-item__head"><strong>M15-SC1</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A startup fine-tunes a downloaded base model on scraped support transcripts. List the four supply-chain decisions and the control for each.</p><p class="sas-answer__label">Model answer</p><p>Base model: pin a digest, record the licence, and prefer a publisher with a signed release. Scraped data: filter personal data, scan for injection patterns, record provenance and review a sample. Training code and dependencies: lockfile with hashes and no unpinned Git installs. Output artefact: convert to safetensors, hash every file, sign the manifest and re-run a safety and refusal evaluation before deployment. Each decision has an owner and an artefact, otherwise the pipeline cannot be audited after an incident.</p></div>

<div class="sas-answer" id="m15-sc2-answer"><p class="sas-item__head"><strong>M15-SC2</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A partner sends a model bundle that passes its own manifest check. Describe what you would do before loading it, and why the manifest is not enough.</p><p class="sas-answer__label">Model answer</p><p>Obtain the expected digest through a separate channel, verify the signature or compare the digest with what the partner published, and inspect the file list for unexpected serialisation formats. Load weights only from a data-only format in a sandbox without credentials, and compare behaviour on a fixed probe set against the documented card. The manifest is not enough because it travels with the bundle, so an attacker who modifies a file can update the list; only an independent trust anchor links content to the publisher.</p></div>

<div class="sas-answer" id="m15-p1-answer"><p class="sas-item__head"><strong>M15-P1</strong> <span class="sas-meta">Practical programming · 8 marks</span></p><p class="sas-answer__q">Write `verify(bundle_dir, manifest)` that hashes every listed file, reports mismatches and refuses to load any file with a pickle-like suffix. Demonstrate it on a clean and a tampered bundle.</p><p class="sas-answer__label">Model answer</p><p>A complete implementation reads the manifest, hashes each listed file with SHA-256 and compares the full digest, then checks the directory for suffixes such as `.pkl`, `.pickle`, `.pt` or `.bin` and raises before any load. Output is a table of expected and actual prefixes with a match flag, plus the refusal path. Demonstrating on two bundles shows the tampered one failing while the documentation file may still match, which is the detail that makes the exercise convincing.</p></div>

<div class="sas-answer" id="m15-ct1-answer"><p class="sas-item__head"><strong>M15-CT1</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">A colleague argues that model hubs are safe because they scan uploads. Assess the argument and its limits.</p><p class="sas-answer__label">Model answer</p><p>Scanning raises the cost of naive attacks and catches known malicious formats, which is worthwhile. It cannot establish that a model behaves safely: a backdoor or a subtly degraded refusal behaviour passes any format scan, and a scanner's coverage is unknown to you. Trust should therefore rest on a pinned digest, a publisher identity, a data-only format and your own behavioural evaluation, with hub scanning treated as one filter among several. The argument's error is treating a platform control as a substitute for your own acceptance decision.</p></div>

<div class="sas-answer" id="m15-ct2-answer"><p class="sas-item__head"><strong>M15-CT2</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">You can fine-tune a strong base model on weak internal data, or train a small model from scratch on curated data. Argue the security trade-off.</p><p class="sas-answer__label">Model answer</p><p>Fine-tuning inherits capability and inherits risk: the base model's provenance, licence and unknown behaviours come with it, and the fine-tune can remove safety behaviour while adding data-driven triggers. Training from scratch gives full control of the data and architecture but produces a weaker model and still depends on libraries, tokenisers and hardware. The decision turns on whether the task needs general capability: if it does, fine-tune with pinned artefacts and a post-tune safety evaluation; if not, the smaller controlled model has a smaller and more auditable supply chain.</p></div>
