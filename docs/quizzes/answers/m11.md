## Multiple-choice explanations

**1. M11-Q01** — correct answer **D: One token sequence in which role markers are ordinary tokens**

Role labels are formatting produced by the template; the transformer sees one sequence, which is why instructions in data can compete with instructions from the operator.

- **A** — Privilege is enforced by the application, not by the separator tokens.
- **B** — The model generates over tokens; it does not parse a protocol object.
- **C** — Earlier turns are usually retained within the context window.

**2. M11-Q02** — correct answer **C: Sampling from the output distribution is stochastic and depends on the seed**

Decoding samples from a distribution shaped by temperature and top-p, so a fixed prompt yields a set of outcomes unless the sampler is made deterministic.

- **A** — Weights are fixed between requests unless retrained.
- **B** — Tokenisation is deterministic for fixed input.
- **D** — Context is managed by the caller, not randomly erased.

**3. M11-Q03** — correct answer **B: The instruction is text in the same channel as attacker input, so it can be overridden**

A rule expressed as tokens competes with other tokens; confidentiality requires keeping the secret out of the model's context, not asking it to keep quiet.

- **A** — Encoding is one bypass among many, not the root cause.
- **C** — Models can often reproduce substantial parts of a prompt.
- **D** — Closed models are equally susceptible.

**4. M11-Q04** — correct answer **A: Scoping tools per user and per task with explicit confirmation**

Impact is bounded by what the assistant can do, so per-task scoping and confirmation limit what a successful injection can achieve.

- **B** — Broad permissions turn a text problem into an action problem.
- **C** — Persistent memory increases both privacy exposure and injection persistence.
- **D** — A larger window admits more untrusted text, not less risk.

**5. M11-Q05** — correct answer **D: Context and cost exhaustion, plus inclusion of untrusted text and personal data**

Large inputs consume the context budget, cost money per token and import whatever the document contains, including instructions and personal data.

- **A** — Refusal is a behaviour question, not the primary concern.
- **B** — Tokenisers handle long input; the limit is the context window.
- **C** — Caching is a deployment choice, not a consequence of length.

**6. M11-Q06** — correct answer **C: The secret is now recoverable from the model's context and possibly its outputs**

Secrets belong in the tool layer, where the model requests an action and the application authenticates; anything in context can be elicited, logged or memorised.

- **A** — Length is a secondary concern compared with disclosure.
- **B** — Passwords tokenise normally, which is the problem.
- **D** — Correct use does not mitigate disclosure.

**7. M11-Q07** — correct answer **B: Agents can take actions with the application's authority**

The consequence of a successful injection changes from a bad answer to an unauthorised action, which is why authorisation must live outside the model.

- **A** — Model size is unrelated to the distinction.
- **C** — Both are injectable; the difference is impact.
- **D** — Agents need stronger, not weaker, identity controls.

**8. M11-Q08** — correct answer **A: The tools, data sources and identities the feature can reach**

Capability determines impact: what the feature can read, write and invoke matters more than the phrasing of its instructions.

- **B** — Wording matters for injection, but capability sets the ceiling on harm.
- **C** — Sampling affects reproducibility, not authority.
- **D** — Uptime is availability, not security.

**9. M11-Q09** — correct answer **D: Logs accumulate personal data, secrets and injected content outside the model's controls**

Prompt logs become a secondary store of sensitive text with its own access, retention and breach exposure, often less protected than the primary system.

- **A** — Performance impact is minor and unrelated to the risk.
- **B** — Logging does not change the context window.
- **C** — Searchability is a benefit, not the risk.

**10. M11-Q10** — correct answer **C: They are ordinary tokens produced by the chat template and can appear in user input**

Templates insert markers such as role names as text; because they are tokens, user input that mimics them can confuse the model's reading of who said what.

- **A** — No cryptographic separation exists in the token stream.
- **B** — The model sees them; that is how it distinguishes turns.
- **D** — Transformers do not require them.

Boundaries are enforced by code that decides which tools exist, which data can be retrieved and what output is allowed.</p></div>

<div class="sas-answer" id="m11-s2-answer"><p class="sas-item__head"><strong>M11-S2</strong> <span class="sas-meta">Short answer · 3 marks</span></p><p class="sas-answer__q">Name two effects of a larger context window on security, one positive and one negative.</p><p class="sas-answer__label">Model answer</p><p>Positive: more retrieved evidence can be included, which can improve grounding and citation. Negative: more untrusted text enters the model at once, which increases injection surface, cost and the amount of personal data processed per request.</p></div>

<div class="sas-answer" id="m11-c1-answer"><p class="sas-item__head"><strong>M11-C1</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">Explain why 'the model is stateless' is both true and misleading for a deployed assistant.</p><p class="sas-answer__label">Model answer</p><p>The model call is stateless: each request is a fresh forward pass over the tokens supplied. The application, however, keeps conversation history, memory stores, retrieved documents and caches, and it resends them or summarises them into later requests. Security-relevant state therefore exists outside the weights, which is why injection can persist across turns and why deletion must cover transcripts, memories and indexes rather than only the model.</p></div>

<div class="sas-answer" id="m11-c2-answer"><p class="sas-item__head"><strong>M11-C2</strong> <span class="sas-meta">Conceptual · 5 marks</span></p><p class="sas-answer__q">An LLM feature is described as 'read-only'. Explain what you must verify before accepting that description.</p><p class="sas-answer__label">Model answer</p><p>Read-only describes the intended tool set, not the actual authority. Verify the credentials the service holds, whether any tool can write through a side effect such as sending email or creating a share link, whether retrieved documents can be modified, and whether the model can influence a downstream system that then acts. Also check that the read scope is tenant-limited and that the identity used is the user's rather than a service account with broad access. The claim is acceptable only when the permissions, not the description, support it.</p></div>

<div class="sas-answer" id="m11-sc1-answer"><p class="sas-item__head"><strong>M11-SC1</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A legal team wants an assistant that summarises contracts and can email the summary to a colleague. Identify the four exposures that must be addressed before launch.</p><p class="sas-answer__label">Model answer</p><p>Confidentiality: contracts are privileged material, so retrieval must be scoped per matter and per user. Injection: contract text is untrusted and may contain instructions, so the model must not be able to choose recipients. Outbound action: email must be limited to internal domains with explicit confirmation and an audit record. Retention: prompts, summaries and retrieved chunks must follow the matter's retention and deletion rules. Each exposure is an interface or identity control, not a prompt instruction.</p></div>

<div class="sas-answer" id="m11-sc2-answer"><p class="sas-item__head"><strong>M11-SC2</strong> <span class="sas-meta">Scenario-based · 6 marks</span></p><p class="sas-answer__q">A support assistant is given access to a ticket system, a knowledge base and a refund tool. Describe how you would reduce its authority without breaking the workflow.</p><p class="sas-answer__label">Model answer</p><p>Scope each capability to the requesting customer: ticket reads limited to that customer's tickets, knowledge base filtered to published articles, and refunds capped by amount and frequency with a human approval step above the cap. Replace any service-wide credential with a delegated token that names the customer, and log every tool call with the effective principal. The workflow survives because the assistant still performs the task for the legitimate case; only the cross-customer and high-value paths require a human.</p></div>

<div class="sas-answer" id="m11-p1-answer"><p class="sas-item__head"><strong>M11-P1</strong> <span class="sas-meta">Practical programming · 8 marks</span></p><p class="sas-answer__q">Write `assemble(system, user, docs, limit)` that builds a prompt within a token budget, never truncates the system component, and labels every untrusted component. Show the component budget table.</p><p class="sas-answer__label">Model answer</p><p>A complete implementation tokenises each component, admits the system component in full, then allocates remaining budget to user text and retrieved documents in a stated priority order, truncating only untrusted content and marking truncation explicitly. It returns the assembled string plus a table of requested and admitted tokens per component. A strong answer treats labels as formatting rather than protection, and notes that truncation of retrieved text can remove the very passage that justifies an answer, so citations must record which chunks were admitted.</p></div>

<div class="sas-answer" id="m11-ct1-answer"><p class="sas-item__head"><strong>M11-CT1</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">A vendor says their assistant 'cannot be jailbroken because the system prompt is proprietary'. Assess the claim.</p><p class="sas-answer__label">Model answer</p><p>Proprietary wording raises the cost of a targeted attack but leaves the mechanism untouched: the model still follows instructions found in its context, and attackers iterate against behaviour rather than source. The claim also confuses secrecy with enforcement, since no prompt wording can prevent an instruction from being overridden. A meaningful claim names the tested attacks, the number of attempts, the success criteria and the residual rate, and it is supported by capability limits such as an allowlist, not by the prompt's confidentiality.</p></div>

<div class="sas-answer" id="m11-ct2-answer"><p class="sas-item__head"><strong>M11-CT2</strong> <span class="sas-meta">Critical thinking · 6 marks</span></p><p class="sas-answer__q">You must choose between a larger context window and a retrieval pipeline for a 10,000-page corpus. Argue the security consequences of each.</p><p class="sas-answer__label">Model answer</p><p>A larger window puts more untrusted text in front of the model per request, raising injection surface and cost, and it provides no access control: everything admitted is equally visible to the model, so a single request can cross tenants. Retrieval introduces a filterable boundary, which is the security advantage, at the cost of new components: an index with its own ACL, embedding inversion risk and deletion lag. Choose retrieval for multi-tenant or sensitive corpora because authorisation must happen before the model reads anything, and use the window only for the few chunks the request legitimately needs.</p></div>
