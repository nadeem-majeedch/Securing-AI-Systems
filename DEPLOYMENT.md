# Deployment

How the course site is built, validated and published to GitHub Pages, and what the owner must do to enable it. This is maintenance documentation: students never need it.

> **Status.** `.github/workflows/pages.yml` and `scripts/verify_site.py` exist in the working tree and have been validated locally. **Nothing has been committed, pushed or deployed, and GitHub Pages is not enabled.** The owner performs those steps; §4 lists them in order.
>
> Until then the repository is a course in a repository, not a published site.

---

## 1. What is deployed, and where

A static site — HTML, CSS, JavaScript, downloadable notebooks and data — generated by `mkdocs build` into `site/`. There is no server-side component, no database, no accounts and no API. Nothing on the published site accepts input from a visitor.

| | |
|---|---|
| **Hosting** | GitHub Pages, published from a GitHub Actions workflow (not from a branch) |
| **URL** | <https://nadeem-majeedch.github.io/Securing-AI-Systems/> |
| **Base path** | `/Securing-AI-Systems/` — a **project site**, not a user site at the domain root |
| **Source of truth** | `main`. The published site is always the output of the latest successful run on `main` |
| **Build output** | `site/` (git-ignored locally; uploaded as the Pages artifact) |
| **Size** | ~26 MiB, ~250 files — well inside the 1 GiB / 20 000-file Pages limits |

**The base path is not optional.** A user site lives at `https://<user>.github.io/`, but a repository site lives one level down. A link written as `/modules/01-introduction/` resolves to `https://nadeem-majeedch.github.io/modules/...` and 404s. Everything that addresses this is in one place: `site_url` in `mkdocs.yml`.

| If this changes | Change this |
|---|---|
| Repository renamed or moved | `site_url` in `mkdocs.yml`, then rebuild |
| Custom domain | `site_url` (must be the custom domain), plus a `CNAME` file in `docs/` so MkDocs copies it into the build, plus DNS |
| Organisation site instead of project site | `site_url` to the bare domain; the base path check in `verify_site.py` should then be relaxed to `/` |

## 2. Required repository settings

All of these are owner actions in the GitHub web interface. None of them is performed by the workflow, and none requires a personal access token.

| Setting | Where | Required value | Why |
|---|---|---|---|
| Default branch | Settings → General | `main` | The workflow triggers on pushes to `main` only |
| Pages source | Settings → Pages → Build and deployment → Source | **GitHub Actions** | Not "Deploy from a branch": a branch deployment would publish the repository root, not the built site |
| Workflow permissions | Settings → Actions → General → Workflow permissions | **Read repository contents** (the default) | The workflow asks for nothing more; the deploy job's `pages: write` and `id-token: write` are declared in the YAML and granted per job |
| Actions allowed | Settings → Actions → General | All actions, or "Allow `actions/*`" | Every action in the workflow is first-party (`actions/checkout`, `actions/setup-python`, `actions/upload-pages-artifact`, `actions/deploy-pages`) |
| Environment | Settings → Environments → `github-pages` | Created automatically on the first deployment | Carries the deployment URL and optional protection rules |
| Secrets | Settings → Secrets and variables → Actions | **None required** | The workflow uses only the ephemeral `GITHUB_TOKEN`; nothing is stored |
| Fork pull requests | Settings → Actions → General | Default is fine | The workflow does not run on `pull_request`, so a fork cannot trigger a deployment |

**Optional hardening, recommended after the first successful deploy:** add a deployment branch rule to the `github-pages` environment (Settings → Environments → `github-pages` → Deployment branches → `main` only). The workflow already refuses to deploy from any other branch; the rule makes that a platform guarantee rather than a workflow convention.

**Do not add:** a personal access token, a `GH_PAGES_TOKEN` secret, or `pages: write` at workflow level. None is needed, and removing them later is harder than never adding them.

## 3. How the workflow operates

File: `.github/workflows/pages.yml`.

### 3.1 Triggers

| Trigger | Effect |
|---|---|
| `push` to `main` | Build, validate, deploy |
| `workflow_dispatch` | Manual run from the Actions tab. On `main` it deploys; from any other branch it builds and validates but the deploy job is skipped by its `if:` condition |

### 3.2 Jobs and permissions

| Job | Runs on | Permissions | What it does |
|---|---|---|---|
| `build` | `ubuntu-latest` | `contents: read` | Checks out, installs the documentation dependencies, checks links, builds with `--strict`, verifies the output, uploads the Pages artifact |
| `deploy` | `ubuntu-latest` | `pages: write`, `id-token: write` | Deploys the artifact to the `github-pages` environment and reports the live URL |

The workflow-level default is `contents: read`; each job restates exactly what it needs. Nothing in the file can write to the repository, and the build job cannot deploy.

### 3.3 Build steps, in order

| Step | Command | Fails when |
|---|---|---|
| Checkout | `actions/checkout` with `persist-credentials: false` | — (the token is not written into `.git/config`, so a build step cannot push) |
| Python | `actions/setup-python`, 3.12, `cache: pip` | — |
| Pin check | inline script over `requirements-docs.txt` | Any requirement is a range rather than `==`; an unpinned build is not reproducible |
| Install | `pip install -r requirements-docs.txt` | Resolution fails. Only the documentation surface is installed — never `requirements-labs.txt`, so a documentation build cannot pull PyTorch |
| Link check | `python scripts/check_links.py` | A relative link or anchor does not resolve, including links in the repository's own documents |
| Build | `python -m mkdocs build --strict` | A page is missing from `nav`, a reference is unresolved, or MkDocs emits any warning |
| Verify | `python scripts/verify_site.py site --base-path /Securing-AI-Systems/` | See §3.4 |
| Upload | `actions/upload-pages-artifact`, path `site`, retention 1 day | Artifact exceeds Pages limits |

`mkdocs.yml` supplies `site_url`, so the build emits canonical URLs, a sitemap, and footer links that include the base path. `use_directory_urls` stays at its default: `modules/06-adversarial-ml.md` is published as `modules/06-adversarial-ml/`, which is what makes the site hostable under a subpath without rewriting.

### 3.4 What `verify_site.py` enforces

The build succeeding is not the same as the site working. This script checks the artefact:

1. `index.html`, `404.html`, `sitemap.xml`, the search index, the stylesheet, the scripts and the vendored Mermaid are all present.
2. Every `href` and `src` in every page resolves to a file in the build — including hand-written HTML links that MkDocs does not rewrite, and anchors (`#…`) that must exist in the target page.
3. No root-absolute internal link escapes `/Securing-AI-Systems/`.
4. Canonical URL and sitemap carry the configured `site_url`.
5. The search index parses, has one entry per page or more, and uses relative locations.
6. At least one page uses the vendored diagram renderer, and no page references `unpkg.com` or any other CDN.
7. No analytics host, no token-shaped string, no absolute local path, no `instructor/` directory.
8. The artefact is inside the 1 GiB and 20 000-file Pages limits.

### 3.5 Concurrency and repeat runs

`concurrency: {group: pages, cancel-in-progress: false}`. A second push queues behind the first instead of cancelling it: cancelling a run mid-deploy can leave the published site half-updated. To force a rebuild without a code change, use **Actions → Deploy course site to GitHub Pages → Run workflow**.

### 3.6 Why there is no `configure-pages` step

`actions/configure-pages` exists to derive a base path for generators that need one injected at build time. MkDocs does not: `site_url` in the configuration already carries the base path, and the verifier checks that the output agrees. Skipping the action removes a step that would otherwise need write access, and the workflow stays two actions lighter. Pages must therefore be enabled before the first deploy — see §4.

### 3.7 Updating the action pins

Actions are pinned to full commit SHAs with the release in a comment, so a tag cannot be moved under the workflow. To bump one:

```bash
# current release and its commit, e.g. for checkout
curl -s https://api.github.com/repos/actions/checkout/releases/latest | grep tag_name
curl -s https://api.github.com/repos/actions/checkout/commits/<tag> | grep '"sha"' | head -1
```

Then replace both the SHA and the comment on one line, and open a pull request. Do not replace a SHA with a floating tag.

## 4. How the owner enables Pages

In this order. Steps 1–4 are one-time.

1. **Commit and push** the workflow, `mkdocs.yml` and `scripts/verify_site.py` to `main`. Nothing deploys yet.
2. **Open Settings → Pages.**
3. **Set Source to "GitHub Actions"** and save. Do not choose "Deploy from a branch": that publishes the repository root, which is a directory listing, not a website.
4. *(Optional, recommended)* **Settings → Environments → `github-pages` → Deployment branches: `main` only.**
5. **Run the workflow once**: Actions → *Deploy course site to GitHub Pages* → *Run workflow* → branch `main`. Or push any commit to `main`.
6. **Watch the run** in the Actions tab. The deploy job prints the site URL; the environment record links to it.

Expected result on the first run: the `build` job takes about two minutes; the `deploy` job takes under a minute; the site appears at <https://nadeem-majeedch.github.io/Securing-AI-Systems/> within a couple of minutes of the deployment reporting success.

If Pages is **not** enabled when the deploy job runs, it fails at its first step with an error naming the Pages site (typically `Get Pages site failed` / `Not Found`). That is not a workflow bug: enable Pages with the Actions source and re-run the job.

## 5. How to identify a successful deployment

Five signals, in order of authority:

| Signal | Where | What it looks like |
|---|---|---|
| **Run status** | Actions tab | A green tick on the run; both `build` and `deploy` succeeded |
| **Deployment record** | Repository → Deployments, or the `github-pages` environment | The deployment is marked **Active**, with the environment URL |
| **Deploy step log** | The `deploy` job | `Reported success`, and `page_url: https://nadeem-majeedch.github.io/Securing-AI-Systems/` |
| **Pages settings** | Settings → Pages | "Your site is live at …" with the same URL |
| **The site itself** | A browser | The home page renders with the navy theme, the diagrams draw, search returns results |

A green run proves the build and the upload. It does **not** prove the published pages are correct on their real origin, so check these once per release:

```bash
base=https://nadeem-majeedch.github.io/Securing-AI-Systems

curl -sI  "$base/" | head -1                       # 200
curl -sI  "$base/modules/06-adversarial-ml/" | head -1
curl -sI  "$base/assets/stylesheets/extra.css" | head -1
curl -sI  "$base/search/search_index.json" | head -1
curl -s   "$base/" | grep -o 'rel="canonical" href="[^"]*"'   # must carry the base path
curl -s -o /dev/null -w '%{http_code}\n' "$base/this-page-does-not-exist/"   # 404
```

Then in a browser: open the home page, follow **Start learning**, open one diagram (it must draw, not sit empty), run a search, and open one notebook download. Five minutes, once per release.

**What success does not mean.** The site being live is not the same as the course being ready to advertise: `LICENSING.md` D-01 is still open, and §9 is the gate that decides whether the content should be public yet.

## 6. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Deploy job fails with `Get Pages site failed`, `Not Found`, or `Resource not accessible by integration` | Pages is not enabled, or is set to "Deploy from a branch" | Settings → Pages → Source: **GitHub Actions**, then re-run the job |
| `Branch "main" is not allowed to deploy to github-pages due to environment protection rules` | Environment branch rule excludes the ref | Run from `main`, or widen the rule |
| Build fails on "not found in `nav`" or a warning | `--strict` doing its job: a page exists without a nav entry, or a link/reference is broken | Add the page to `nav` in `mkdocs.yml`, or fix the link. Run `python -m mkdocs build --strict` locally first |
| `check_links.py` fails | A relative link, anchor or directory URL does not resolve | Run it locally; the message names the file and the target |
| `verify_site.py` fails on "root-absolute link escapes the base path" | A link was written as `/modules/...`, or `site_url` was changed without rebuilding | Write the link relative, or fix `site_url` |
| `verify_site.py` fails on a missing anchor | A `#fragment` link points at a heading that was renamed | Rename the heading or the link |
| Site loads but is unstyled | Pages is serving the repository root rather than the build, or the artifact path is wrong | Confirm the Pages source is GitHub Actions and the upload path is `site` |
| Pages 404 on every page except home | Base path mismatch: `site_url` does not match the published URL | Correct `site_url`, rebuild, redeploy |
| Deploy succeeds but the site shows old content | Browser or CDN cache | Hard-reload; if it persists, confirm the run's commit is the latest on `main` |
| `Resource not accessible by integration` in the build job | A step needs a permission the build job does not have | Add it to that job only, never to the workflow default |
| Run fails at "Confirm documentation dependencies are exactly pinned" | Someone added `package>=1.2` to `requirements-docs.txt` | Pin the exact version |
| Artifact upload fails on size or file count | The build exceeds 1 GiB or 20 000 files | Check for committed binaries or a vendored dataset; `verify_site.py` reports both numbers |
| Workflow does not run on a push | Push was not to `main`, or Actions is disabled for the repository | Check the branch, and Settings → Actions → General |
| Deprecation warning about a Node runtime in an action | An action pin is old | Bump the SHA and its comment (§3.7) |

## 7. How to update the website

### Routine change

```bash
python -m mkdocs serve                  # http://127.0.0.1:8000 — edit and review
python scripts/check_links.py           # links and anchors
python -m mkdocs build --strict         # production build
python scripts/verify_site.py site --base-path /Securing-AI-Systems/
```

Then commit and push to `main`. The workflow rebuilds and republishes; there is no file to copy and no server to restart.

### Checking project-site hosting before pushing

The local dev server serves the site at `/`, which hides base-path mistakes. Reproduce the deployed layout:

```bash
python -m mkdocs build --strict
rm -rf .pages-test && mkdir -p .pages-test/Securing-AI-Systems
cp -r site/. .pages-test/Securing-AI-Systems/
python -m http.server 8123 --directory .pages-test
# open http://127.0.0.1:8123/Securing-AI-Systems/
```

Delete `.pages-test/` afterwards; it is not part of the repository.

### Rolling back

Revert the offending commit on `main` and push. The workflow republishes the previous state within a couple of minutes. Do not try to redeploy an old artifact: Pages artifacts are kept for one day, and a revert is reproducible where an artifact is not.

### Renaming the repository

Update `site_url` in `mkdocs.yml`, update the base path default in `scripts/verify_site.py` if the name changed, rebuild, and push. GitHub keeps the old Pages URL redirecting for a while, but the canonical URLs in the new build point at the new path immediately.

## 8. Reproducing CI locally

The workflow runs exactly these commands. If they pass locally on the same Python minor version (3.12) they will pass in CI, with one exception noted below.

```bash
python -m pip install -r requirements-docs.txt
python scripts/check_links.py
python -m mkdocs build --strict
python scripts/verify_site.py site --base-path /Securing-AI-Systems/
```

**The exception:** GitHub Actions execution itself cannot be verified from this machine. The YAML parses, the permissions and triggers are reviewed, the commands are the same, and the pins resolve to real releases — but whether GitHub accepts and runs the workflow is only provable by pushing it. Treat the first run on `main` as the acceptance test for the workflow, and the local checks as the acceptance test for the site.

## 9. Pre-publication checklist

Nothing is published unless every box is checked. The first five are enforced by the workflow; the rest are human decisions.

- [ ] `python -m mkdocs build --strict` completes with zero warnings.
- [ ] `python scripts/check_links.py` passes.
- [ ] `python scripts/verify_site.py site` passes.
- [ ] `site/` contains **no** path beginning with `instructor/`.
- [ ] The build contains no analytics, CDN reference, token or absolute local path (checked by the verifier).
- [ ] **Licensing status is accurate on every surface**: the footer, [Credits and attribution](docs/attribution.md), `README.md` §23 and `docs/references.md` say the same thing, and say "no licence recorded" until D-01 is signed.
- [ ] If licence files exist, they are published, the scope matches `LICENSING.md` §3.2, and the footer no longer says "pending".
- [ ] `ATTRIBUTION.md` is current for every dependency and vendored file.
- [ ] [Privacy](docs/getting-started/privacy.md) and [Academic integrity](docs/getting-started/academic-integrity.md) render and are in the navigation.
- [ ] Search spot-checked on the published site: "prompt injection" returns results, and no result is a 404.
- [ ] The 404 page serves for an unknown path.
- [ ] The owner has explicitly authorised publication.

## 10. Safety properties this deployment preserves

| Property | Why it matters | How it is enforced |
|---|---|---|
| Instructor material never published | Answer keys in a public site destroy assessment integrity | `exclude_docs` in `mkdocs.yml`, plus a verifier assertion that `site/instructor/` does not exist |
| No secrets in content | A public history is permanent | No secrets are configured; the verifier scans the build for token-shaped strings; `.gitignore` covers `.env` |
| No third-party trackers or requests | The course teaches privacy; a tracker would contradict it | No analytics, no CDN, vendored Mermaid, system fonts. The verifier fails on an analytics host or an `unpkg.com` reference |
| Least privilege | A compromised build step must not be able to write to the repository | `contents: read` by default; `pages: write` and `id-token: write` only on the deploy job; no PAT anywhere |
| Reproducible builds | The published site must match a commit | Exact pins in `requirements-docs.txt`, a pin check in CI, `--strict`, and a SHA-pinned action set |
| Licence status is honest | An unlicensed site that looks open invites reuse the owner cannot authorise | One statement, repeated on four surfaces, and checked in §9 |
| Third-party material stays attributed | Losing attribution turns citation into copying | `ATTRIBUTION.md` updated with any dependency; no ISO/IEC text or paper figure in the build |

## 11. What this document does not authorise

Creating the Pages site, changing repository settings, committing, pushing, publishing a release and deploying are owner actions. Preparing and validating the workflow is not permission to perform them, and a session that touches this repository must not describe the site as published until the owner has confirmed the deployment.
